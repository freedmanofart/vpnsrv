# Подключение Freedom VPN на мобильном клиенте по коду провайдера

Мобильный клиент использует существующий device API. Отдельный обход
авторизации или передача сервисных секретов на телефон не нужны. Операторская
утилита находится в `scripts/issue_provider_code.py`, её тесты — в
`tests/test_issue_provider_code.py`.

## Подготовка backend

Нужен существующий пользователь с `telegram_id`, активной подпиской и
назначенным активным VLESS-клиентом на рабочем inbound/child 3x-ui. Код не
создаёт подписку, сервер или VPN-клиента. Наличие и срок подписки проверяются в
VPN Admin; нода должна быть доступна и синхронизирована с master/child 3x-ui.
Дополнительные миграции сверх действующего device API не требуются.

## Тестовая доставка кода в Telegram

API может автоматически прислать выпущенный код пользователю через Telegram-
бота. На этапе интеграционного теста доставка ограничена одним точным email:

```dotenv
PROVIDER_CODE_NOTIFICATION_EMAIL=freedmanofart@icloud.com
```

Пустое значение полностью отключает уведомления с provider-кодами. Для любого
другого email API продолжит выпускать код оператору, но не отправит его в
Telegram. Сопоставление нечувствительно к регистру и не использует username,
поэтому смена Telegram username не изменит allowlist.

Уведомление содержит восьмизначный код, готовое значение для обязательного поля
`Имя устройства` (`Мой телефон`), срок действия и краткий путь в приложении.
Код в БД хранится только в виде хеша и не записывается в audit log. В
`audit_logs.details.notification_sent` сохраняется только результат доставки.

На сервере или машине оператора с Python и `httpx`:

```bash
python scripts/issue_provider_code.py \
  --api-url https://PUBLIC_API_HOST \
  --telegram-id 123456789 \
  --ttl-minutes 10
```

Подставьте действительные API URL и Telegram ID. Утилита читает
`SERVICE_API_TOKEN` из окружения или запрашивает его скрытым вводом. Не
передавайте токен аргументом командной строки. HTTPS проверяется, redirect не
выполняется; HTTP разрешён только для localhost. Ответ содержит восьмизначный
код, включая возможные начальные нули, и срок действия. Код показывается
оператору один раз — не публикуйте его в CI или Git.

## Сценарий на телефоне

1. Выбрать `Добавить` → `Провайдер`.
2. Ввести восемь цифр и имя устройства.
3. Нажать `Получить конфигурацию`.
4. Выбрать доступную ноду из загруженного списка.
5. Проверить подключение созданного профиля.

Адрес API задаётся при сборке клиента через `VPNCLIENT_BACKEND_URL`. Он должен
совпадать с origin, на котором выпущен код. Шестизначный email-код
web-кабинета для этого сценария не подходит.

## API-контракт

### 1. Выпуск кода оператором

`POST /v1/client/activation-codes`

Авторизация: `Authorization: Bearer SERVICE_API_TOKEN`.

```json
{
  "telegram_id": 123456789,
  "ttl_minutes": 10
}
```

Ответ:

```json
{
  "code": "00123456",
  "expires_at": "2030-01-01T00:00:00Z"
}
```

### 2. Активация телефона

`POST /v1/client/activate` без сервисного токена:

```json
{
  "code": "00123456",
  "name": "iPhone Артема",
  "platform": "ios"
}
```

Код состоит ровно из восьми цифр, является одноразовым и блокируется в БД при
погашении. Ответ содержит scoped device token, `device_id` и `expires_at`.
Токен сохраняется в защищённом хранилище клиента.

### 3. Получение профиля

`GET /v1/client/profile` с device Bearer token возвращает доступные ноды и
VLESS-конфигурации. Сервисный токен и доступ к 3x-ui телефону не передаются.

Пустой `nodes` означает отсутствие назначенного активного VPN-клиента. HTTP
`403` означает отсутствие активной подписки. `available=false` запрещает выбор
недоступной ноды.

### 4. Обновление токена

`POST /v1/client/refresh` с действующим device Bearer token выдаёт новый токен.
Старый токен после этого немедленно перестаёт работать. Отзыв устройства
выполняется в VPN Admin в разделе `Устройства`.

## Приёмка

- несуществующий Telegram-пользователь отклоняется;
- правильный код создаёт устройство и открывает профиль;
- повторное погашение и истёкший код отклоняются;
- при отсутствии активной подписки профиль отвечает понятной ошибкой;
- недоступная нода возвращается с `available=false` и не выбирается клиентом;
- сервисные секреты и полные конфигурации отсутствуют в обычных логах;
- перед публичным тестом проверены ограничения частоты `/activate` на reverse
  proxy/API.

Ошибка REALITY после успешного импорта относится к VPN-туннелю, а не к выдаче
кода. Установка APK не развёртывает backend и не выпускает тестовый код сама.

## Проверки

Локальные тесты утилиты:

```bash
python -m unittest discover -s tests -p test_issue_provider_code.py
```

Полный жизненный цикл device API проверяет существующий скрипт:

```bash
python scripts/e2e_device_profile.py
```

Он создаёт и отзывает реальное устройство, поэтому используйте отдельного
тестового пользователя. Публичный код выдавайте только после проверки
правильного API origin.
