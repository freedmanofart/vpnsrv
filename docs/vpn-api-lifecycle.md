# Логика VPN API: тарифы, оплата и выдача доступа

## Границы ответственности

VPN API хранит коммерческое и прикладное состояние в PostgreSQL: пользователей,
тарифы, платежи, подписки, выбранные страны и историю клиентов. 3x-ui master
хранит сетевую конфигурацию inbound и реально разрешённых в Xray клиентов.
Telegram-бот и web admin не изменяют Xray напрямую: они вызывают VPN API, а API
синхронно обращается к REST API 3x-ui master.

Одна активная подписка пользователя соответствует одному активному клиенту.
Клиент привязан к логической ноде, а логическая нода — к одному VLESS inbound
3x-ui. Страна хранится в `vpn_nodes.region` как `<ISO>|<название>` и выбирается
до оплаты или перевыпуска.

## Основные сущности

### Пользователь

`users` связывает внутренний ID с Telegram-пользователем. Все платежи,
подписки и клиенты ссылаются на внутренний `user_id`. Удаление Telegram-диалога
не удаляет доступ из 3x-ui.

### Тариф

`plans` задаёт:

- стабильный уникальный `code`;
- отображаемое название;
- цену и валюту;
- продолжительность в днях;
- лимит одновременных IP-подключений `max_connections`;
- квоту трафика `traffic_limit_gb`;
- признаки `is_active` и `is_public`.

`max_connections` передаётся в 3x-ui как `client.limitIp`: `1` разрешает один
одновременный исходный IP, `3` — три, `0` — снимает ограничение. Это не число
сохранённых профилей и не HWID-регистрация устройства. 3x-ui также имеет
`limitHwid`, но этот режим требует совместимого клиента и отдельного процесса
регистрации устройств, поэтому текущие тарифы его не используют.

Публичная сетка: «Лайт» — 5 IP и 250 ГБ, «Стандарт» — 15 IP и 650 ГБ,
«Ультра» — 30 IP и 3 ТБ. VPN API переводит квоту в байты и отправляет её в
3x-ui как `totalGB`. Новый лимит применяется при создании или перевыпуске ключа.

`GET /plans` возвращает только активные публичные тарифы. Неактивный тариф
нельзя купить или использовать для нового продления. Изменение цены влияет
только на новые платежи: сумма копируется в запись платежа при его создании.
Исторический тариф лучше отключать, а не удалять, поскольку на него ссылаются
старые подписки и платежи.

В web admin у тарифа доступны «Изменить» и «Удалить». `DELETE /plans/{id}`
физически удаляет только тариф, на который ещё не ссылаются подписки и платежи.
Для использованного тарифа API возвращает `409`; его следует сделать
неактивным через «Изменить», сохранив коммерческую историю.

### Платёж

`payments` фиксирует пользователя, тариф, выбранную ноду, сумму, валюту,
провайдера, ID операции провайдера и параметры будущего клиента. Связь с
`subscription_id` появляется только после успешной оплаты и выдачи доступа.

Допустимые состояния и переходы:

```text
pending -> processing -> paid -> refunded
   |          |          
   +----------+-----> failed | cancelled | expired
```

Из конечных состояний `failed`, `cancelled`, `expired` и `refunded` переходы
не выполняются. Внешние `success` и `succeeded` нормализуются в `paid`, а
`canceled` — в `cancelled`.

### Подписка

`subscriptions` хранит оплаченный период: `starts_at`, `expires_at` и состояние
`active`, `expired` или `cancelled`. Доступ определяется одновременно статусом
и временем: активной считается запись `status=active` с `expires_at > now`.

### VPN-клиент

`vpn_clients` — версия выданного ключа. Для каждого перевыпуска создаётся новая
строка и новый UUID; старые строки не переиспользуются и остаются историей со
статусом `revoked`. Служебный идентификатор в 3x-ui — `vpn-<client_id>`.
Именно по нему API выполняет удаление, поэтому вручную созданный в панели
клиент не входит в управляемый жизненный цикл.

## Выбор страны и подготовка ноды

Бот получает доступные страны через `GET /vpn/nodes`. В выдачу входят только
активные логические ноды, способные принимать клиентов. При выборе страны её
`node_id` сохраняется в создаваемом платеже, а после оплаты определяет inbound.

Конфигурация ноды содержит URL 3x-ui master и ID inbound, а также публичный
шаблон ссылки. Для текущего профиля обязательны:

- внешний host и порт VPN inbound;
- `type=xhttp`, `security=reality`, `encryption` из VLESS inbound;
- `fp=firefox`, SNI, Reality public key, short ID и spiderX;
- `path=/`, `mode=auto`, xHTTP host;
- `x_padding_bytes=100-1000` и эквивалентный JSON в `extra`.

ML-KEM `encryption` относится к inbound, а не к отдельному пользователю.
Следовательно, у клиентов одной страны разные UUID и комментарии, но общий
сетевой шаблон выбранного inbound. Между странами encryption, public key,
short ID, spiderX, адрес и порт могут различаться.

## Создание платежа

`POST /payments` получает `user_id`, `plan_id`, `node_id` и уникальный
`idempotency_key`. Перед обращением к провайдеру API проверяет пользователя,
активность тарифа и активность ноды. Сумма и валюта берутся с сервера из
тарифа, поэтому клиент не может назначить цену самостоятельно.

Одинаковый `idempotency_key` всегда возвращает уже существующий платёж. Это
защищает от двойного нажатия кнопки, повтора HTTP-запроса и сетевого timeout.
По умолчанию провайдер создаёт платёж в `pending`. В тестовом режиме
`PAYMENT_AUTO_CONFIRM=true` API сразу проводит внутреннее событие `paid`; в
production подтверждение должно приходить подписанным webhook провайдера.

## Обработка webhook оплаты

Провайдер вызывает `POST /payments/webhooks/{provider}` и передаёт ID события,
подпись и тело. API проверяет подпись до изменения данных. Пара
`provider + event_id` уникальна и записывается в `payment_events`, поэтому
повторная доставка одного webhook безопасна и возвращает прежний результат.

Строка платежа блокируется `SELECT ... FOR UPDATE`, затем проверяется допустимость
перехода. Для `paid` без связанной подписки выполняется выдача доступа в одной
логической операции:

1. блокируется пользователь;
2. проверяется отсутствие другой действующей подписки;
3. создаются подписка и VPN-клиент с новым UUID и сроком тарифа;
4. в выбранный inbound 3x-ui добавляется клиент `vpn-<id>` с UUID, временем
   окончания (`expiryTime` в миллисекундах), Telegram ID и тарифным лимитом
   одновременных IP (`limitIp`);
5. фиксируются подписка, клиент, платёж и событие;
6. `subscription_id` сохраняется в платеже.

Если 3x-ui не добавил клиента, транзакция PostgreSQL откатывается. Если 3x-ui
успел добавить клиента, но commit БД завершился ошибкой, компенсация удаляет
нового клиента из 3x-ui. Платёж не должен считаться успешно обработанным, пока
выдача не завершилась целиком; API возвращает ошибку provisioning для повтора
или ручного разбора.

## Формирование и выдача ключа

VPN URI строится только из UUID активного клиента и конфигурации выбранной
ноды. Все интерфейсы — Telegram, личный кабинет и web admin — используют один
генератор, поэтому формат не расходится. Fragment имеет вид `vpn-<client_id>` и
нужен только как понятное имя профиля.

Полная ссылка является секретом. В аудит и обычные логи её записывать нельзя.
Пользователю возвращается только его активный, не истёкший клиент. Наличие
строки в PostgreSQL без соответствующего клиента в inbound считается
рассинхронизацией и исправляется reconciliation или перевыпуском.

## Продление

`POST /subscriptions/{id}/renew` продлевает срок и одновременно меняет ключ.
Если подписка ещё действует, новый период добавляется к текущему `expires_at`;
если срок уже закончился, отсчёт начинается от текущего времени.

Порядок защищает от двух одновременно действующих ключей:

1. создаётся новый UUID и клиент в состоянии `provisioning`;
2. новый клиент добавляется в тот же inbound;
3. старый клиент удаляется из 3x-ui;
4. старый клиент помечается `revoked`, новый — `active`;
5. подписка получает новый срок и `active`;
6. изменения фиксируются транзакцией.

Если удалить старого клиента не удалось, API пытается удалить уже созданного
нового клиента и откатывает БД. Таким образом, ошибка продления не должна
оставить два управляемых ключа.

Важно: текущий `/renew` — административная операция и сам по себе не проверяет
новый платёж. Обычный `paid` сейчас создаёт новую подписку и отклоняется при уже
существующей активной подписке; автоматической связи «повторный платёж →
renew» пока нет. Поэтому платное продление следует вызывать из доверенного
процесса только после подтверждения оплаты. Не меняйте `expires_at` вручную без
обновления клиента в 3x-ui.

## Перевыпуск и смена страны

`POST /subscriptions/{id}/rotate` создаёт новый UUID, но не добавляет время.
Запрос содержит целевой `node_id`; поэтому тот же маршрут обслуживает как
компрометацию ключа, так и перенос в другую страну.

Сначала клиент создаётся в целевом inbound. Затем старый удаляется из его
исходного inbound, даже если страна изменилась. Только после этого статусы
фиксируются в PostgreSQL. При ошибке удаления старого клиента новый удаляется
компенсационной операцией. Если активного старого клиента уже нет, создаётся
новый — это позволяет восстановить доступ после массового отзыва ключей.

## Истечение и отзыв

Worker периодически ищет истёкшие активные клиенты и подписки. Клиент сначала
удаляется из соответствующего inbound 3x-ui и только затем получает `revoked`.
Подписка становится `expired` после успешного отзыва всех её активных клиентов.
Если master временно недоступен, состояние остаётся активным для следующей
попытки: база не заявляет об отзыве, который физически не произошёл.

Webhook `refunded` отзывает все активные клиенты связанной подписки и переводит
подписку в `cancelled`. Если отзыв в 3x-ui не удался, refund-событие завершается
ошибкой provisioning и должно быть повторено после восстановления связи.

## Управление платежами в web admin

Раздел «Платежи» показывает сохранённую сумму, валюту, провайдера, статус и
связанную подписку. Для ожидающего платежа администратор может подтвердить,
отметить ошибку или отменить его; для оплаченного — зарегистрировать возврат.
Эти кнопки не являются косметическим редактированием поля:

- `paid` запускает обычную атомарную выдачу подписки и клиента в 3x-ui;
- `refunded` отзывает ключ и отменяет подписку;
- каждый ручной переход записывает отдельное payment event и audit event;
- недопустимый повторный переход возвращает `409`, ошибка 3x-ui при выдаче или
  отзыве не должна превращать платёж в успешно обработанный.

Ручное подтверждение предназначено для разбора платежа, уже проверенного во
внешней системе. Оно не заменяет webhook и не доказывает факт поступления денег.

Чек ручного перевода хранится в записи платежа как binary, MIME type и имя
файла. Защищённый маршрут web admin отдаёт фактическое изображение или документ;
Telegram `file_id` сохраняется в `details` только как служебная ссылка.

`GET /users/{telegram_id}/vpn-status` читает live-счётчики из `clientStats`
разрешённого маршрута `GET /panel/api/inbounds/list` 3x-ui. Отдельный маршрут
`/clients/traffic/{email}` текущему node-sync токену недоступен (`403`). При
временной ошибке панели бот показывает сохранённую тарифную квоту.

Раздел «Способы оплаты» управляет Telegram-кнопками: названием, URL, порядком и
активностью. Начальные способы: СБП/QR, карта в рублях, зарубежная карта,
крипта, Telegram Stars и справка о безопасности. Пустой URL означает, что способ
виден, но ещё не подключён. Для Stars дополнительно нужна цена в XTR.

## Reconciliation

Worker сравнивает активных клиентов PostgreSQL со списком клиентов inbound.
Он использует только служебные email `vpn-<id>`, поэтому не должен принимать
чужие ручные записи за управляемые. После аварии проверьте health ноды и
запустите `POST /vpn/nodes/{id}/reconcile`. Массовое удаление клиентов следует
выполнять только после backup; строки в БД переводятся в `revoked`, а не
удаляются физически.

## Операционная проверка

Перед продажами и после изменения inbound проверьте:

1. `/health` и `/db-health`;
2. `GET /vpn/nodes` и health каждой активной страны;
3. доступ master к внешнему HTTPS child с валидным сертификатом;
4. совпадение inbound ID, публичного порта и всех Reality/XHTTP параметров;
5. тестовую покупку с уникальным idempotency key;
6. наличие ровно одного `vpn-<id>` в нужном inbound;
7. импорт и реальное подключение выданной URI;
8. перевыпуск и отсутствие старого клиента;
9. отсутствие ошибок worker после цикла reconciliation/expiration.

Коды `409` обычно означают уже существующую активную подписку, `400` —
недопустимый профиль или переход, `502` — ошибку 3x-ui, `503` — недоступную
локацию или отсутствующую конфигурацию.
